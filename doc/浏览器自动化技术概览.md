## 一、核心概念介绍

### CDP（Chrome DevTools Protocol）

CDP 是 Chrome/Chromium 暴露的底层调试协议，基于 WebSocket + JSON-RPC。所有上层工具（Puppeteer、Playwright 的 Chromium 驱动）都在 CDP 之上构建。它能做的事包括：操控 DOM、拦截网络请求、执行 JS、截图、调试内存/性能，本质上是浏览器把内部能力"接管"给外部程序。

**协议 vs 代码**：CDP 本身是一份规范文档（定义消息格式、命令名、参数结构），不是可运行的代码——类比 HTTP 协议，HTTP 是规则，不是程序。实现这份规范的才是代码：

```
CDP 协议（规范文档）
  ├─ Chromium 内部实现了 CDP Server（监听 WebSocket，执行指令）← 代码
  └─ Playwright/Puppeteer 实现了 CDP Client（发指令、收响应）  ← 代码
```

类比 HTTP：Nginx 是服务端实现，requests 是客户端实现，HTTP 规范本身只是一份文档。

**直接用 CDP 的场景**：上层工具满足不了需求时（如监控特定 V8 堆事件、细粒度 Network 拦截、自定义 DevTools 扩展）。

---

### Chromium

Google Chrome 的开源版本，是大多数浏览器自动化工具的底层引擎。Puppeteer 和 Playwright（Chromium 模式）会在安装时自动下载固定版本的 Chromium，以保证行为一致性。

**软件、浏览器、进程是同一个东西的不同侧面**：
- **软件**：安装包/二进制文件，静态躺在磁盘上
- **浏览器**：它的功能定位（渲染网页、执行 JS）
- **进程**：启动后 OS 把它加载进内存，就变成一个运行中的进程

注意：Chromium 和完整 Chrome 有细微差异（如 Widevine DRM、某些媒体解码器），做反爬攻防时需注意"浏览器指纹"识别。

---

### Puppeteer

Google 出品的 Node.js 库，封装了 CDP，专门控制 Chromium/Chrome。API 设计直觉清晰，"页面操作"是核心抽象。只支持 Chromium 系浏览器（新版也开始支持 Firefox，但生态仍以 Chrome 为主）。

```js
const browser = await puppeteer.launch();
const page = await browser.newPage();
await page.goto('https://example.com');
const title = await page.title();
await browser.close();
```

---

### Playwright

Microsoft 出品的自动化**库**（`pip install playwright`），支持 Chromium、Firefox、WebKit 三引擎，支持 Python/TypeScript/Java/C# 多语言。

**Playwright 的本质**：一段寄生在你程序进程里的代码，但它干的事是**启动一个新进程（Chromium），然后通过 CDP 协议控制它**。

```
你的 Python 进程
    └─ Playwright 库（寄生在你的进程里）
              └─ 启动 → Chromium 进程（独立应用程序）
              └─ 通过 WebSocket/CDP 发指令 → Chromium 执行操作
```

和普通库（如 requests）的区别：
- requests：在你的进程里直接发 HTTP 请求，全程一个进程
- Playwright：启动 Chromium 作为独立进程，通过协议遥控它，始终是两个进程

**容器化场景下的进程模型（重要）**：

容器不等于进程，容器是隔离的运行环境，里面可以有多个进程。以本项目的 `browser-worker` 容器为例：

```
browser-worker 容器（Docker 隔离环境）
  ├─ Python 进程（Celery worker，PID 1 或其子进程）
  │     └─ Playwright 库（寄生在 Python 进程内存里）
  │               └─ p.chromium.launch() → 在容器内 fork 出 Chromium 进程
  │                         ↕ WebSocket / CDP
  └─ Chromium 进程（任务执行期间存在，任务结束后关闭）
```

关键结论：
- Playwright 库本身在 Python 进程里（不占独立进程）
- Chromium 是被 Playwright **在同一个容器内** fork 出来的独立进程
- 这就是为什么必须用 `mcr.microsoft.com/playwright/python` 官方镜像——它同时提供 Python 环境 + Chromium 二进制，两者都在同一个容器里，Playwright 才能找到并启动 Chromium

与"远程浏览器"方案的对比（未采用，仅做理解参考）：

```
# 本项目用的方案：Playwright 与 Chromium 同容器
browser-worker 容器
  ├─ Python/Celery
  └─ Chromium（同容器内，Playwright 直接 launch）

# 另一种方案：Chromium 单独容器，通过 CDP 远程连接
python-worker 容器          chrome 容器
  └─ Python/Celery    →→→   └─ Chromium（--remote-debugging-port=9222）
     playwright.connect()         监听 WebSocket
```

本项目选同容器方案，省去维护独立 Chrome 容器和网络配置的复杂度。

```python
from playwright.sync_api import sync_playwright

with sync_playwright() as p:
    browser = p.chromium.launch()   # 启动 Chromium 进程
    page = browser.new_page()
    page.goto("https://example.com")  # 通过 CDP 协议控制 Chromium 打开页面
    print(page.title())
    browser.close()                 # 关闭 Chromium 进程
```

### Headless Browser（无头浏览器）

"无头"是一种运行模式，而非特定产品：浏览器在没有 GUI 窗口的情况下运行，通常用于服务器环境。Chromium、Firefox 都支持 `--headless` 参数。Puppeteer 和 Playwright 默认即以 headless 模式启动。

与有头模式的区别：无头下某些反爬检测更容易命中（如 `navigator.webdriver` 标志），需额外处理。

---

### Storage State（Playwright 特有）

Playwright 提供的登录态持久化方案，把浏览器的 cookies + localStorage 导出为一个 JSON 文件。下次启动新的浏览器上下文时加载这个文件，即可直接恢复登录态，无需重新走登录流程。

```python
# 导出登录态
context.storage_state(path="state.json")

# 加载登录态
context = browser.new_context(storage_state="state.json")
```

## 二、对比表格

| 维度 | CDP | Chromium | Puppeteer | Playwright | Headless 模式 |
|---|---|---|---|---|---|
| **类型** | 底层协议 | 浏览器引擎 | JS 自动化库 | 多语言自动化框架 | 运行模式 |
| **多浏览器支持** | 仅 Chrome/Edge | 单引擎 | 仅 Chromium（为主） | Chromium + Firefox + WebKit | 取决于底层工具 |
| **语言** | 协议无关 | — | Node.js | Python/TS/Java/C# | — |
| **API 抽象层** | 无（原始协议） | — | 中等 | 高（auto-wait、Locator） | — |
| **安装复杂度** | 低（直连 WebSocket） | 需自行管理二进制 | `npm i puppeteer`（自动下载 Chromium） | `pip install playwright` + `playwright install chromium` | 无额外安装 |
| **调试工具** | Chrome DevTools 本体 | — | `--inspect`、`slowMo` | `--debug`、Playwright Inspector、Trace Viewer | 可切有头模式调试 |
| **反爬规避** | 精准控制（可注入 JS） | — | 需手动处理（stealth 插件） | 内置部分规避，也需 stealth 插件 | 无头下指纹更易被识别 |
| **测试场景** | 不适合 | — | 有（jest + puppeteer） | 专业测试工具（内置断言、报告、并发） | 标准做法 |
| **登录态持久化** | — | — | 手动处理 Cookie | 内置 Storage State | — |
| **典型用途** | 自定义工具/DevTools 扩展 | 作为依赖被调用 | 爬虫、截图、PDF 生成 | 端到端测试、复杂爬虫 | CI/服务器自动化 |
| **维护主体** | Google | Google | Google | Microsoft | — |

## 三、实际场景举例

### 场景 1：爬取动态渲染页面（如本项目的雪球抓取）

雪球板块页面是纯前端渲染，没有独立 JSON 接口，必须用真实浏览器执行。

```python
# 在已登录页面内发起 API 请求，带上浏览器 Cookie
data = page.evaluate("""
    fetch('/v5/stock/screener/industries.json')
        .then(r => r.json())
""")
```

**选 Playwright 的原因**：
- 支持 Storage State 持久化登录态，一次导出服务器长期复用
- `page.evaluate()` 在已登录页面内执行 fetch，带上 Cookie，绕过 API 匿名限制
- auto-waiting 减少硬等待

---

### 场景 2：绕过新浪 K 线反爬

新浪历史 K 线接口（`quotes.sina.cn`）纯 requests 约 250 只后触发永久 456 拒绝。用 Playwright 控制 Chromium 在页面内 fetch，携带真实浏览器指纹，可连续抓 500+ 只不失败。

```python
js = """async (url) => {
    const r = await fetch(url, {credentials: 'include'});
    return {status: r.status, text: await r.text()};
}"""
result = page.evaluate(js, url)
```

---

### 场景 3：自动化端到端测试

```typescript
import { test, expect } from '@playwright/test';

test('用户登录后可以看到首页', async ({ page }) => {
  await page.goto('http://localhost:8090');
  await page.fill('#username', 'admin');
  await page.fill('#password', 'secret');
  await page.click('button[type=submit]');
  await expect(page.locator('.dashboard')).toBeVisible();
});
```

---

### 场景 4：直接操控底层 CDP（高级）

```python
# 监听所有网络请求的原始 headers
cdp = page.context.new_cdp_session(page)
cdp.send("Network.enable")
cdp.on("Network.requestWillBeSent", lambda e: print(e["request"]["url"]))
```

## 四、选型建议

```
需要多浏览器测试（Safari 兼容）       → Playwright
已有 Node.js 技术栈，只需 Chrome     → Puppeteer
需要精细控制底层网络/内存/调试事件    → 直接用 CDP
跑 CI / 服务器无 GUI 环境            → 任意工具 + Headless 模式
反爬要求高（模拟真人）                → Playwright + stealth + 有头模式
服务器保持登录态                      → Playwright Storage State
```
