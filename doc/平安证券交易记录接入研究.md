# 平安证券交易记录接入研究

## 结论

当前项目已经支持用户从平安证券导出成交查询 TXT，再上传到「我的」页面导入交易记录。

暂不建议让服务器直接登录用户的平安证券账户并自动抓取交易记录。公开可访问的平安证券网站未发现面向普通个人用户、可申请授权的交易查询开放 API；自动化登录通常还会涉及短信/验证码、设备风控、登录态保存和接口变更。

## 当前已有能力

- 前端「我的 → 实盘复盘」支持上传 TXT。
- 后端支持平安证券成交查询 TXT 的 GBK 编码。
- 支持历史成交和当日成交两种格式。
- 按用户隔离交易记录。
- 重复导入会按用户、标的、日期、方向、价格、数量去重。
- 导入成功后自动同步「持仓」和「清仓」分组。

相关代码：

- `backend/app/api/routers/public/trades.py`
- `backend/app/repositories/trades.py`
- `frontend/src/pages/My.tsx`

## 自动接入的可行性

### 方案 A：官方授权 API

如果平安证券后续为个人用户提供正式 API 或第三方授权入口，这是最推荐的方案。需要确认：

- 是否支持查询历史成交、当日成交和持仓；
- 是否有 OAuth 或其他授权机制；
- 是否允许第三方应用保存授权令牌；
- 是否有明确的个人开发者使用条款和接口限额。

### 方案 B：用户导出文件导入

当前方案，风险最低，建议优先完善：

- 支持 CSV、Excel 和更多平安导出格式；
- 导入前展示解析预览，用户确认后入库；
- 增加券商来源和导入批次；
- 使用成交编号/委托编号去重，避免同价同量同日交易被误判为重复；
- 支持导入持仓和资金流水，但不把资金数据混入交易记录。

### 方案 C：本地浏览器自动化

理论上可以在用户本机打开平安证券网页，由用户手动完成登录和验证码，再读取页面或下载的成交文件。这个方案不应把证券密码上传服务器，且只能作为个人本地工具研究，不适合作为云端公共功能。

### 方案 D：服务器代登录抓取

不建议。主要问题是验证码和风控导致不稳定，用户证券凭据和登录态的安全责任较重，接口改版也会导致功能突然失效。项目也不应保存用户证券密码或要求用户把密码发给开发者。

## 推荐开发顺序

1. 先完善当前 TXT 导入：预览、错误行提示、批次记录和更可靠的成交编号去重。
2. 让用户可以手动导入持仓和资金流水，完善实盘资产总览。
3. 关注平安证券是否提供正式开放 API；若有，再按授权 API 设计接入。
4. 不实现服务器保存证券密码的自动登录方案。
