## 一、问题背景

大 V 观点复盘支持按日期查询大量历史文章，并为每篇文章中的标的计算 1、3、5、7、10、20、60、120 个交易日收益率和沪深 300 超额收益。

原实现虽然已经加入复盘快照，但对没有完成快照的文章仍采用逐篇、逐标的查询方式：

1. 先读取文章列表；
2. 每篇文章单独查询个股行情；
3. 每个标的重复查询沪深 300 行情；
4. 每篇文章单独写入快照并提交事务。

这种模式属于典型的 N+1 查询，历史文章数量增加后，接口响应时间明显变长，前端可能在接口完成前主动取消请求并出现 499。

## 二、本阶段完成内容

### 1. 个股行情批量读取

复盘服务先完成文章和观点匹配，收集本次请求实际涉及的去重股票代码，再通过一次 SQL 查询读取全部相关行情，并限制为本次请求最早文章日期之后的数据，避免加载无关的全部历史行情。

### 2. 沪深 300 只查询一次

沪深 300 基准行情从标的循环中移出，改为一次读取。之后按文章日期在内存中定位未来交易日序列，计算各复盘窗口的基准收益和超额收益。

### 3. 内存字典匹配

批量查询结果按股票代码建立索引：

```text
quotes_by_code[code] -> 该股票的行情序列
```

文章只访问自己涉及的代码，不再扫描全部股票。整体计算复杂度由大量数据库往返降低为：

```text
O(M + N × W + T)
```

其中 `M` 为文章数量，`N` 为去重后的股票数量，`W` 为最多 121 个交易日，`T` 为文章中的标的提及次数。

### 4. 快照批量写入

新增 `save_review_snapshots()`，将本次复盘产生的多个快照通过一次批量 upsert 写入数据库，减少逐文章打开连接、执行 SQL 和提交事务的开销。

### 5. 快照完成条件调整

只要文章存在有效标的，并且所有标的的八个复盘窗口都有行情数据，即可标记为完成快照。没有结构化观点但正文自动匹配到标的的文章也可以进入完成状态。

观点提取或人工映射发生变化时，原有快照仍会自动失效并重新计算。

## 三、性能验证

本地真实 PostgreSQL 数据测试结果：

| 查询范围 | 优化前 | 优化后 |
|---|---:|---:|
| 近 30 天 | 约 5.56 秒 | 约 5.00 秒 |
| 近 90 天 | 约 9.62 秒 | 约 7.45 秒 |

此前服务器近 90 天复盘曾超过 35 秒，并被前端取消；批量查询后，近 90 天本地测试已降至约 7.45 秒。

同时确认：

- PostgreSQL 没有发现锁等待；
- API、数据库和 Redis 容器资源正常；
- 行情字段为 PostgreSQL `double precision`，JSON 快照序列化正常；
- 后端测试：`4 passed`；
- Python 编译检查通过；
- `git diff --check` 通过。

## 五、部署说明

服务器更新时执行：

```bash
cd /data/app
git checkout dev
git pull --ff-only origin dev
bash deploy_server.sh
```

部署后首次查询尚未完成快照的历史范围时，会批量读取行情并生成快照；后续查询优先复用已完成快照。

## 六、当前限制

- 首次计算完全没有快照的超大历史范围时，仍需要一定处理时间；
- 复盘接口目前仍是同步请求，后续可进一步改为后台任务加进度展示；
- 观点结构化提取仍需要通过观点提取任务生成，正文自动识别只是没有结构化观点时的回退机制；
- 快照按文章保存，按日合并仅影响展示，不改变底层复盘粒度。

## 七、阶段结论

本阶段完成了大 V 复盘的批量行情查询和批量快照写入，消除了核心行情查询的 N+1 结构，并限制了内存加载范围。复盘接口在本地真实数据上的近 90 天耗时由约 9.62 秒降至约 7.45 秒，为后续后台异步复盘和进度化展示提供了稳定基础。
