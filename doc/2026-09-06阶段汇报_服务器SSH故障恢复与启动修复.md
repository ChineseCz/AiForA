# 2026-09-06 阶段汇报：服务器 SSH 故障恢复与启动修复

| 项目 | 内容 |
|---|---|
| 文档类型 | 运维故障处理汇报 |
| 处理日期 | **2026-09-06** |
| 服务器 | 腾讯云 Ubuntu 22.04 |
| 公网地址 | `124.222.169.60` |
| 当前状态 | SSH 已恢复，服务器可正常启动 |

## 一、故障现象

服务器原系统无法通过公网 SSH 登录，客户端连接 TCP 22 端口失败。进入腾讯云救援模式后，救援系统中的 SSH 服务可以正常启动并监听 22 端口，说明公网 IP、安全组和基础网络链路基本正常，问题集中在原系统启动过程和系统配置。

## 二、故障定位

原系统启动日志显示：

```text
Timed out waiting for device /dev/vdb
```

进一步检查 `/etc/fstab` 发现存在旧的挂载配置：

```text
/dev/vdb /data ext4 defaults 0 2
```

但腾讯云控制台和系统 `lsblk` 均确认当前实例只有 40GB 系统盘 `/dev/vda2`，没有 `/dev/vdb` 数据盘。因此系统启动时等待不存在的设备，最终进入 `emergency mode`，SSH 服务未能正常进入可用状态。

## 三、处理过程

### 1. 检查并修复系统文件系统

确认根分区为 `/dev/vda2` 后，在救援环境中执行文件系统检查：

```bash
fsck -f -y /dev/vda2
```

检查结果显示文件系统元数据存在不一致，工具完成了日志恢复、extent tree 优化和空闲块计数修复，并提示：

```text
FILE SYSTEM WAS MODIFIED
```

### 2. 修复原系统挂载配置

通过 `chroot /mnt` 进入原系统文件环境，修改 `/etc/fstab`，将不存在的数据盘配置调整为非阻塞挂载：

```text
/dev/vdb /data ext4 defaults,nofail,x-system.device-timeout=5s 0 2
```

随后执行：

```bash
mount -a
```

确认配置语法和挂载检查无报错。

### 3. 修复 SSH 配置

确认 `/etc/ssh/sshd_config` 中已启用密码认证，并允许 root 登录：

```text
Port 22
PermitRootLogin yes
PasswordAuthentication yes
```

使用以下命令验证 SSH 配置：

```bash
sshd -t
systemctl enable ssh
```

`sshd -t` 无输出，表示配置语法正确。由于操作发生在 `chroot` 环境中，`systemctl restart ssh` 不会在救援环境中实际重启服务，因此通过正常重启让原系统重新加载配置。

## 四、恢复验证

服务器恢复正常启动后，确认：

```bash
findmnt -T /data/app
df -hT /data/app
```

结果表明：

```text
/data/app 位于 /dev/vda2
系统盘容量：40G
已用空间：23G
可用空间：16G
```

项目目录当前约占用：

```text
134M    /data/app
```

公网 SSH 端口验证成功：

```text
Connection to 124.222.169.60 22 port [tcp/ssh] succeeded!
```

服务器已可以通过公网 SSH 登录，项目文件也正常存在。

## 五、数据结论

腾讯云控制台确认当前实例此前没有独立数据盘。`/data/app` 实际位于系统盘 `/dev/vda2`，因此本次 `/dev/vdb` 缺失不是数据盘数据丢失，而是遗留的无效 `/etc/fstab` 配置导致的启动阻塞。

本次处理未执行格式化、重新分区或初始化操作，项目数据未被破坏。

## 六、后续建议

1. 保留 `/etc/fstab` 中的 `nofail` 和设备超时配置，避免非关键挂载点阻塞系统启动；如果确认永远不存在 `/dev/vdb`，可直接删除或注释该挂载项。
2. 为 `/data/app` 建立定期备份，至少保留远程 Git 仓库、云端备份或压缩归档三种方式中的一种。
3. 定期检查系统盘空间，当前系统盘可用约 16GB，部署依赖和日志增长后需要持续关注。
4. SSH 恢复后建议优先使用普通用户加 SSH 密钥登录，并关闭不必要的 root 密码登录。

## 七、结论

本次服务器 SSH 故障根因是 `/etc/fstab` 等待不存在的 `/dev/vdb`，导致 Ubuntu 启动进入 `emergency mode`。通过救援模式完成文件系统检查、挂载配置修复和 SSH 配置验证后，服务器已恢复正常启动，公网 SSH 已恢复，项目数据保持完整。
