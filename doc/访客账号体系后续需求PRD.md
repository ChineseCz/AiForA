## 1. 忘记密码（邮箱账号） ✅ 已完成

**动机**：邮箱账号目前只有注册和登录，忘记密码没有任何找回入口，只能联系管理员改库。这是账号体系的基本缺口，用户量一大必然会被问到。

**方案**：
- 复用现有邮箱验证码发送逻辑（`email/send-code` 的 Redis key 换个前缀，如 `resetcode:{email}`，避免和注册验证码混用导致"注册中"和"找回中"互相冲突）。
- 新增 `POST /api/user/email/reset-password`：校验邮箱+验证码后，允许直接设置新密码（不需要旧密码，因为已经过邮箱验证码这一层身份核实）。
- 前端 `VisitorLogin.tsx` 邮箱登录 Tab 加"忘记密码"链接，复用 `EmailRegisterTab` 的验证码交互模式（发码→倒计时→提交）。

**实现结果**：新增邮箱重置验证码和重置密码接口，验证码使用独立 Redis key、发送限流并避免暴露邮箱是否注册；登录页将邮箱登录和邮箱注册合并到同一个“邮箱” Tab，内部切换登录/注册，登录模式下直接显示“忘记密码”入口。

## 2. 三种登录方式账号互通（绑定/合并）

**动机**：现在手机号、邮箱、微信是三张互不关联的"影子账号"。同一个人换设备/换登录方式会变成一个新账号，昵称、（未来可能有的）个性化设置都丢失。

**方案（简单版，推荐先做这版）**：
- 登录后在账号菜单加"绑定邮箱"/"绑定手机号"入口：已用微信登录的用户，可以给当前 `users` 行补上 `email` 或 `phone` 字段（走验证码校验），而不是创建新行。
- 复杂的"合并两个已存在的账号"（比如手机号账号和邮箱账号已经分别注册过，现在要合成一个）先不做——数据迁移逻辑复杂（历史数据关联、冲突处理），且当前系统里"账号"还没有绑定业务数据（没有收藏/关注等），合并的紧迫性低。
- 如果后续账号绑定了实际业务数据（比如"我的自选股分组"迁到访客账号下），再重新评估是否需要账号合并。

**工作量**：中。需要给 `require_visitor` 之外设计"半鉴权"绑定接口（已登录状态下追加字段+唯一性冲突处理）。

## 3. 短信服务真实接入

**动机**：`services/external/sms.py` 是 Mock，手机号登录目前形同虚设（验证码只打日志），前端 Tab 也因此被临时移除。

**方案**：
- 办理阿里云短信服务或腾讯云短信资质（需要企业资质/签名报备，非纯技术工作，用户侧需要先完成）。
- 资质办好后，`send_sms` 函数体换成真实 SDK 调用，`user_auth.py` 调用方不用改。
- `VisitorLogin.tsx` 把手机号 Tab 加回来（代码里的注释已经说明位置）。

**工作量**：技术工作量小（就是替换一个函数体），但依赖外部资质审批周期（通常几天到两周）。

## 4. 注册/登录安全加固

**动机**：当前验证码发送限流是 IP 维度（slowapi `1/minute`）+ 邮箱/手机号维度（Redis key），没有图片验证码或行为验证，理论上换IP+换邮箱可以批量注册脚本刷。

**当前实现**：
- 邮箱找回密码的“发送重置验证码”增加后端图片数字公式验证码；
- 邮箱注册的“获取验证码”同样增加后端图片数字公式验证码；
- 图片验证码答案存 Redis，5 分钟过期，校验后立即删除，刷新图片会使旧答案失效；
- 验证码答案不返回前端，邮箱是否存在也不通过接口暴露。

**后续方案（按需）**：
- 如果观察到滥用迹象（管理后台 `job_runs`/日志里出现异常密集的注册请求），再引入行为验证码（极验/腾讯云验证码）或简单的蜂窝限流（同一 IP 段每日注册上限）。
- 当前是内部小项目非公开互联网服务，风险可接受，过度设计反而增加登录流程摩擦。

**工作量**：视方案而定，先不做，留作观察后的响应式措施。

## 5. 邮件通知能力扩展（依赖账号体系）

**动机**：账号体系搭好后，"给登录用户发通知邮件"的基础设施（SMTP + 邮箱地址）已经具备。可以考虑：周总结生成完成后给订阅的访客发邮件摘要、大V发新帖时给关注该大V的访客发提醒。

**方案**：
- 需要先有"关注/订阅"这个业务概念（目前访客账号只是登录态，没有和大V/板块产生任何关联数据），这是比通知本身更大的前置需求，建议放在账号绑定/合并（第2项）之后，视产品方向决定是否做。
- 技术上复用现有 `email.py::send_verification_email` 的发送模式（同步SMTP+`run_in_threadpool`），量大时（比如给所有订阅用户群发）要考虑批量发送不要在一个请求里同步跑完，应该走 Celery `default` 队列异步任务。

**工作量**：大，且强依赖产品方向未定的"订阅"功能，暂不评估细节，先记录方向。

## 涉及的既有约定（改动时别违反）

- SMTP/短信发送都是同步IO，走 `run_in_threadpool`，别在事件循环里直接调用（CLAUDE.md"异步/同步分界"）。
- 验证码类接口都要有 Redis 节流（发送间隔 + 有效期），参考 `_email_resend_key`/`_email_code_key` 的写法。
- JWT 的 `typ` 字段（`admin`/`visitor`）是鉴权分层的关键，新接口如果要求登录，明确选用 `require_visitor` 还是 `require_visitor_or_anonymous`。
- 改动后不主动跑 build/重启容器，等用户明确要求。
