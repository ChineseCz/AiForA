# AI Agent 与程序基础学习笔记

> 本文是概念学习笔记，不属于当前项目的功能总结、交付报告或部署文档。

## 一、先建立整体认识

AI Agent 不是一种独立于软件之外的神秘实体，本质上仍然是一个运行中的软件系统。它通常以大模型为决策核心，再配合工具、上下文、记忆和执行循环，完成一个或多个目标。

可以简化为：

```text
Agent = 大模型 + 工具 + 状态/记忆 + 控制循环 + 权限
```

普通聊天更接近：

```text
输入问题 -> 生成回答
```

Agent 更接近：

```text
理解目标
  -> 制定步骤
  -> 调用工具
  -> 观察执行结果
  -> 调整计划
  -> 继续执行
  -> 完成任务或请求人工确认
```

因此，真正需要关注的不是产品是否自称 Agent，而是它能否访问数据、调用工具、连续执行任务、根据结果修正，并且是否有合适的权限隔离。

## 二、Agent 概念从哪里来

Agent 不是最近才出现的产品名词。人工智能研究中早就有“智能体”的概念，通常指能够感知环境、做出决策并采取行动以实现目标的系统。早期相关研究包括智能软件 Agent、多智能体系统等。

大模型时代的变化，主要是把 Agent 的语言理解和决策部分交给了大语言模型。于是原来的程序控制逻辑变成了：

```text
程序负责提供环境、工具和权限
大模型负责理解目标、选择下一步行动
程序继续执行行动并把结果反馈给模型
```

所以“Agent”更多是一个系统架构和交互方式，不是某个特定模型的名称。

## 三、子 Agent 和多 Agent

### 3.1 子 Agent

子 Agent 是主 Agent 委托出去的独立任务执行者。例如让主 Agent 完成一个支付功能时，可以把任务拆成：

```text
主 Agent
  ├─ 子 Agent：分析现有支付代码
  ├─ 子 Agent：设计数据库变更
  ├─ 子 Agent：补充测试
  └─ 主 Agent：汇总结果并修改项目
```

子 Agent 通常拥有独立的任务目标和上下文，也可能有不同的工具权限或工作目录。

“子 Agent”是逻辑概念，不一定真的对应一个操作系统线程。实际实现可能是：

- 同一进程中的多个异步任务
- 多次独立的大模型 API 调用
- 多个操作系统进程
- Docker 容器或远程机器
- 使用不同提示词或不同模型的任务循环

### 3.2 多 Agent

多 Agent 指多个 Agent 协作完成一个复杂目标，重点是任务分工和协调：

```text
需求分析 Agent
  -> 编码 Agent
  -> 测试 Agent
  -> 审查 Agent
  -> 发布 Agent
```

很多所谓的多 Agent 系统，底层可能只是一个程序依次调用同一个模型，但给不同调用分配不同角色、上下文和工具。因此“多 Agent”不必然意味着多个真正并行的进程。

它的价值通常来自：

- 拆分上下文，减少信息混杂
- 让不同任务并行执行
- 给不同角色配置不同权限
- 让结果互相检查

代价是调度更复杂、Token 消耗更高，也可能出现结果冲突。

## 四、几类工具的定位

### 4.1 Codex

Codex 是面向软件研发的 AI Agent。它不只是生成代码，还可以在项目中形成开发闭环：

```text
读取项目
  -> 理解需求
  -> 制定修改方案
  -> 修改文件
  -> 运行命令和测试
  -> 根据结果修复
  -> 检查差异和风险
```

“Codex + 开发流程”的含义就是把 Codex 放进真实的软件工程流程中，而不是只让它单独生成一个函数。

Codex 的优势：

- 理解代码库和文件之间的关系
- 修改多文件功能
- 运行测试、构建和调试命令
- 结合 Git 查看改动和审查结果
- 通过项目规则、Skills、MCP 等扩展开发流程

### 4.2 Hermes Agent

Hermes 更像一个可以长期运行的通用个人 Agent 平台，强调：

- 长期记忆和历史会话搜索
- 技能积累和技能扩展
- Telegram、Discord、Slack 等消息渠道
- 定时任务
- 子 Agent 和并行工作流
- 本地、Docker、SSH、云沙箱等执行环境

它也可以写代码和执行命令，但它的核心价值是让 Agent 持续在线、跨渠道、跨环境地完成任务。

### 4.3 OpenClaw

OpenClaw 和 Hermes 属于同一大类，都是长期运行的个人 AI Agent 系统。

OpenClaw 更强调：

- Gateway 统一管理会话、工具和事件
- 连接 WhatsApp、Telegram、Discord、Slack 等渠道
- 手机或其他设备节点
- 语音、屏幕、摄像头等设备能力
- 技能、插件和模型提供商扩展

两者功能有重叠，通常没有必要同时部署。选择时主要看自己需要的渠道、设备、记忆、定时任务和部署方式。

### 4.4 WorkBuddy

WorkBuddy 更偏办公任务 Agent，适合：

- 生成报告、PPT 和表格
- 整理资料和会议记录
- 分析办公文件和数据
- 生成周报、汇报材料
- 多 Agent 并行处理办公任务

简单分类：

```text
Codex   = 软件研发 Agent
Hermes  = 长期运行的通用个人 Agent
OpenClaw = 多渠道、多设备个人助手 Agent
WorkBuddy = 办公任务 Agent
```

这些边界不是绝对的。Codex 和 Hermes 也可以通过脚本或工具处理文档，WorkBuddy 也可能具备一定代码能力，区别主要在默认工作流和产品优化方向。

## 五、OpenClaw 为什么需要 Gateway

OpenClaw 需要同时连接消息渠道、网页控制台、设备节点、文件系统、工具和定时任务，因此通常会运行一个长期存在的 Gateway。

其结构可以理解为：

```text
Telegram / Discord / WhatsApp
网页控制台
手机或电脑节点
定时任务
        |
        v
     Gateway
        |
        v
模型、会话、记忆、工具、权限
```

Gateway 的职责包括：

- 接收和路由不同渠道的消息
- 管理会话和任务状态
- 调用模型和工具
- 处理事件与定时任务
- 把结果返回给正确的渠道
- 统一处理身份认证和权限

这里的 Gateway 不只是网络代理，更接近一个长期运行的控制中心。

Codex 终端通常围绕当前项目和当前任务工作，结构更简单：

```text
用户 -> Codex -> 当前项目、终端、测试工具
```

因此不一定需要一个面向多渠道的常驻 Gateway。

## 六、程序、进程和线程

### 6.1 程序和进程

- **程序**：磁盘上的静态文件，例如 `python.exe`、`myapp.exe` 或一组源代码。
- **进程**：程序被操作系统加载并运行后的实例。

同一个程序可以同时启动多个进程。比如同时打开两个编辑器窗口，通常就可能对应两个进程实例。

可以记成：

```text
程序 = 要运行的东西
进程 = 正在运行的程序实例
```

### 6.2 进程的组成

一个进程通常包括：

```text
进程
├─ 虚拟地址空间
│  ├─ 代码段
│  ├─ 全局变量和数据段
│  ├─ 堆 heap
│  ├─ 线程栈 stack
│  └─ 动态库
├─ 一个或多个线程
├─ 打开的文件、网络连接和系统句柄
├─ 权限、环境变量和工作目录
└─ 操作系统维护的进程控制信息
```

### 6.3 线程和寄存器

线程是进程内部实际执行代码的路径。每个线程都有自己的：

- CPU 寄存器状态
- 程序计数器，即下一条要执行的指令位置
- 栈
- 调度状态

因此“寄存器里的东西”主要属于线程，而不是整个进程。多个线程可以共享同一进程的代码、堆和全局数据，但各自有独立的执行位置和栈。

可以简化成：

```text
进程 = 地址空间 + 资源 + 一个或多个线程 + 操作系统管理信息
线程 = 寄存器状态 + 执行栈 + 执行位置
```

## 七、虚拟地址空间

虚拟地址空间可以粗略理解为操作系统给进程提供的一大片可使用地址，但它不等于真实内存条上连续的一片区域。

进程看到的是自己的地址视图：

```text
进程虚拟地址 0x1000
        |
        v
操作系统的地址映射
        |
        v
物理内存地址 0xA73000
```

虚拟地址可以映射到：

- 物理内存 RAM
- 硬盘分页文件
- 内存映射文件
- 共享内存
- 设备内存

不同进程甚至可以使用相同的虚拟地址，但映射到不同的物理地址：

```text
进程 A 的 0x1000 -> 物理地址 X
进程 B 的 0x1000 -> 物理地址 Y
```

这样操作系统可以隔离进程，避免一个普通进程直接破坏另一个进程的内存。

虚拟地址空间中的区域通常有不同权限：

- 可读
- 可写
- 可执行

所以更准确地说：

> 虚拟地址空间是一套由操作系统管理的、进程可见的内存地址和映射关系，用来组织代码和数据；它不一定全部对应当前实际占用的 RAM。

## 八、如何选择这些工具

对研发工程师，可以按工作类型选择：

| 需求 | 更适合的工具 |
|---|---|
| 阅读项目、写代码、调试、测试、重构 | Codex |
| 定时检查服务器、监控日志、后台执行任务 | Hermes 或 OpenClaw |
| 通过手机消息控制 AI | Hermes 或 OpenClaw |
| 报告、PPT、表格和办公资料 | WorkBuddy，或让 Codex 通过工具生成 |
| 只是在本地项目中开发 | Codex 通常已经足够 |

最实用的组合通常是：

```text
Codex：负责高质量代码实现和项目验证
Hermes/OpenClaw：负责常驻、定时、消息渠道和外部自动化
WorkBuddy：负责办公资料和正式交付物
```

如果没有明确的常驻、定时、跨设备需求，不必为了“Agent”这个概念额外部署 Hermes 或 OpenClaw。先把 Codex 的项目规则、测试流程、MCP 和 Skills 配置好，通常更直接。

## 九、关键结论

1. Agent 本质上是以大模型为决策核心的程序系统。
2. Agent 的核心不是“会聊天”，而是能规划、调用工具、观察结果并继续行动。
3. 子 Agent 是被主 Agent 委托的独立逻辑任务，不一定是操作系统线程。
4. 多 Agent 是多个任务循环加上协调机制，不一定代表多个真正的模型或进程。
5. Codex 是偏软件研发的 Agent；Hermes 和 OpenClaw 是偏长期运行和外部自动化的通用 Agent。
6. Gateway 是管理多渠道、会话、工具、设备和事件的长期运行控制中心。
7. 程序是静态文件，进程是运行实例，线程是进程内部的执行路径。
8. 寄存器状态主要属于线程；虚拟地址空间属于进程的内存视图。
