# 2026-09-28 阶段汇报：雪球采集登录态过期诊断与修复

## 问题描述

用户报告雪球采集任务虽然显示 `success` 状态，但实际上所有大V都显示"新增 0 条"帖子，数据库中最新的帖子只到 **9月21日**，而实际上很多大V在近期发布了新帖子。

## 问题诊断

### 1. 服务器日志分析

通过 SSH 连接服务器（124.222.169.60），检查了以下内容：

**任务执行记录**：
```sql
SELECT id, kind, status, log FROM job_runs WHERE kind = 'crawl' ORDER BY started_at DESC LIMIT 3;
```

发现所有采集任务日志都显示：
```
✅ （）：新增 0 条
```

**关键症状**：
- 大V名字是空的（括号内为空）
- 每个大V都是"新增 0 条"
- 任务状态显示 `success` 但实际未抓取到数据

**帖子数据验证**：
```sql
SELECT user_id, title, created_at, to_timestamp(created_at/1000) as actual_time 
FROM posts ORDER BY created_at DESC LIMIT 20;
```

确认最新帖子时间戳为 **2026-09-21 07:15:20**（1789974920000 毫秒）

### 2. 根本原因

服务器上的雪球登录态文件 `/data/app/backend/data/xueqiu-state.json` 最后修改时间为 **2026-08-19 10:08**，已过期超过 1 个月。

根据《服务器浏览器Worker部署方案.md》，项目采用**方案 C（Storage State 容器化）**：
- 登录态以 Playwright storage state 格式存储在 `xueqiu-state.json` 文件中
- 雪球登录态通常 30 天左右过期
- 过期后抓取任务无法获取真实内容，导致"新增 0 条"

## 解决方案

### 1. 创建维护脚本目录

在项目根目录下创建 `scripts/maintenance/` 目录，用于存放日常维护脚本。

### 2. 更新雪球登录态流程

**步骤**：
1. 本地运行 `backend/export_xueqiu_state.py` 导出新的登录态
   - 脚本打开 Edge 浏览器（使用 `data/edge_profile/` 登录态）
   - 访问雪球网站，确认登录状态
   - 导出为 `backend/data/xueqiu-state.json`（137KB）

2. 上传到服务器
   ```bash
   scp backend/data/xueqiu-state.json ubuntu@124.222.169.60:/data/app/backend/data/
   ```

3. 重启 browser-worker 容器使新登录态生效
   ```bash
   ssh ubuntu@124.222.169.60 "cd /data/app/backend && docker compose restart browser-worker"
   ```

### 3. 创建自动化维护脚本

创建 `scripts/maintenance/update_xueqiu_login.bat`，集成上述三个步骤为一键式操作：
- 自动激活 Python 虚拟环境（`.venv`）
- 调用导出脚本
- 上传到服务器
- 重启容器
- 执行完成后等待用户确认再关闭窗口（便于查看日志）

### 4. 添加维护文档

创建 `scripts/maintenance/README.md`，说明：
- 脚本用途和使用场景
- 详细的使用方法
- 手动执行命令（不使用批处理脚本时）
- 原理说明
- 相关文档链接

## 技术细节

### SSH 密钥配置

在排查过程中，为了方便后续直接 SSH 连接服务器，配置了 SSH 公钥认证：
- 将本地 SSH 公钥添加到服务器 `~/.ssh/authorized_keys`
- 后续可以免密码连接服务器进行运维操作

### 批处理脚本优化

**问题**：初版批处理脚本未激活虚拟环境，导致找不到 `playwright` 模块

**解决**：在脚本中添加虚拟环境激活逻辑：
```batch
if exist ".venv\Scripts\activate.bat" (
    call .venv\Scripts\activate.bat
    echo Using virtual environment
)
```

### 数据库时间戳格式

**发现**：数据库中 `posts.created_at` 字段存储的是毫秒级时间戳（13位数字），需要除以1000才能转换为正确的日期时间：
```sql
to_timestamp(created_at/1000)  -- 正确
to_timestamp(created_at)        -- 错误，会显示为 58692 年
```
