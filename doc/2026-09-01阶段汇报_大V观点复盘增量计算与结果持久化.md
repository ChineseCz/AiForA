## 一、本阶段背景

大 V 观点复盘支持短线、中线和长线多个交易周期。此前每次打开或刷新复盘页面，都可能重新读取文章并计算行情，历史文章数量较大时会增加数据库查询和接口响应时间。

本阶段将复盘结果持久化到服务器，并根据文章观点状态进行增量更新，避免已经完成的历史文章被重复复盘。

## 二、本阶段完成内容

### 1. 新增复盘快照表

新增 Alembic 迁移 `0030_bigv_review_snapshots.py`，创建表 `bigv_review_snapshots`，保存：

- 文章 ID；
- 复盘结果 JSON；
- 是否已完成全部周期验证；
- 最近更新时间。

数据库已在本地升级到 `0030 (head)`。

### 2. 已完成文章直接复用结果

复盘服务现在会先批量读取文章快照：

- 快照已完成且观点签名一致：直接返回已保存结果；
- 快照未完成：继续查询最新行情并补充可用周期；
- 行情尚未覆盖 120 个交易日：保留未完成状态，后续请求自动继续补算；
- 八个复盘窗口全部有数据后，标记为已完成。

当前复盘窗口为：

```text
1、3、5、7、10、20、60、120 个交易日
```

### 3. 观点变化自动使快照失效

为避免复用过期结果，快照同时保存观点签名。以下操作会删除对应文章的旧快照：

- 重新提取文章观点；
- 观点进入待处理状态；
- 观点提取失败；
- 管理员修改股票代码或股票名称映射；
- 忽略或恢复某条观点。

这样修改观点后，下一次复盘会重新计算，不会继续使用旧标的或旧方向。

### 4. 仓储层增加快照读写能力

在 `app/repositories/opinions.py` 中增加：

- `get_review_snapshots()`：批量读取快照；
- `save_review_snapshot()`：新增或更新快照；
- `delete_review_snapshot()`：删除指定文章快照。

复盘结果仍保持现有接口返回结构，前端无需改动即可使用增量结果。

## 五、部署说明

服务器部署时执行：

```bash
cd /data/app
git checkout dev
git pull --ff-only origin dev
bash deploy_server.sh
```

部署脚本应执行数据库迁移，使服务器升级到 `0030`。升级完成后，复盘接口首次访问会逐步生成历史快照，后续访问优先复用已完成结果。

## 六、当前策略与注意事项

- 未完成快照不会被当作最终结果，行情补齐后仍会继续计算；
- 快照只按文章保存，按日合并展示不会影响底层文章复盘；
- 观点或标的映射发生变化后，旧快照会自动清除；
- Redis 仍用于短期接口缓存，数据库快照用于长期持久化，两者职责不同；
- 首次复盘全部历史文章时仍需要一定时间，完成后后续请求会明显减少重复计算。

## 七、阶段结论

本阶段完成了“大 V 文章观点提取 → 行情验证 → 结果持久化 → 观点变更自动失效”的闭环。复盘系统从每次全量计算升级为可持续补算的增量机制，为后续增加统计报表、观点准确率排行和自动复盘任务打下基础。
