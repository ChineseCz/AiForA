# 排障记录：重建单个容器后管理员登录一直失败

| 项 | 内容 |
|---|---|
| 日期 | 2026-07-12 |
| 现象 | 后台 `/admin/login` 页面登录管理员账号密码，一直失败 |
| 根因 | nginx 反代缓存了后端容器的旧内部 IP，与账号密码无关 |
| 排查耗时 | 约5分钟 |

---

## 1. 现象

用户反馈"管理员登录一直失败"。第一直觉是账号密码错、密码 hash 损坏、或者 JWT 校验逻辑有 bug——但这几个猜测都还没验证就去改代码，是常见的排障陷阱。

## 2. 排查步骤（保留了走过的弯路，不是"标准答案"）

### 第一步：先确认数据层面没问题

```bash
docker compose exec postgres psql -U natapp -d natapp -c "SELECT id, username, LENGTH(password_hash) FROM admins;"
```
返回一行正常的 admin 记录，`password_hash` 长度 60（bcrypt 标准长度）。**数据层没问题**，排除"密码 hash 损坏"这个猜测。

### 第二步：直接打后端接口，绕开前端

```bash
curl -X POST http://localhost:8088/api/admin/login -d '{"username":"admin","password":"admin12345"}'
# 200 {"access_token": "...", ...}
```
后端接口本身完全正常，登录成功拿到 token。**排除鉴权逻辑 bug**——问题不在 `require_admin`/`create_access_token` 这些代码里。

关键教训：**如果后端接口直连是好的，问题必然在"接口到用户之间"的某一层**（前端调用方式 / 反代 / 网络），不会再是后端业务逻辑，不要回头去读 `security.py`/`deps.py` 找 bug。

### 第三步：换成前端实际访问的路径

用户实际是通过 `https://jingfan.nat100.top` 域名访问的，这个域名反代到本机 `8090` 端口（frontend 容器里的 nginx），再由 nginx 反代到 `8088`（api 容器）。直接测这条链路：

```bash
curl -X POST http://localhost:8090/api/admin/login -d '{...}'
# 502 Bad Gateway
```
**复现了**。8088 直连是好的，走 8090（nginx 反代）就 502——问题定位到 nginx 这一层。

### 第四步：看 nginx 的错误日志，不要猜

```bash
docker compose logs frontend --tail 30
```
关键行：
```
connect() failed (111: Connection refused) while connecting to upstream,
upstream: "http://172.23.0.7:8000/api/admin/login"
```
`Connection refused` 说明 nginx 尝试连接的那个 IP（`172.23.0.7`）根本没有进程在监听——不是"权限不够"或"超时"，是**这个 IP 已经不对了**。

### 第五步：定位为什么 IP 不对

回想最近的操作：为了让邮箱 SMTP 配置生效，之前单独跑过：
```bash
docker compose up -d --build api
```
只重建了 `api` 容器，没有动 `frontend`。**Docker 每次重建容器都会分配新的内部 IP**，`api` 容器换了 IP，但 `frontend` 容器里的 nginx 早前已经把旧 IP 解析结果缓存住了（Docker 内置 DNS 在 nginx 这类长连接/常驻进程里不会主动重新解析），一直拿着失效的 IP 去连，自然 `Connection refused`。

## 3. 结论 & 修复

**跟账号密码毫无关系**，是基础设施层的连接问题。

```bash
docker compose restart frontend
```
重启 frontend 让 nginx 重新走一次 DNS 解析，拿到 api 容器的新 IP，恢复正常。

## 4. 复用到以后的经验

1. **分层排查，由外到内 or 由内到外都行，但别跳步**：数据层 → 后端直连 → 反代链路 → 具体某一跳的日志。每一步都能明确"排除了什么"，而不是凭直觉改代码。
2. **"登录失败"这个症状本身信息量很低**，前端弹出的错误提示通常是笼统的"登录失败"，看不出是 401（真的密码错）还是 502（网络层根本没到后端）。遇到"一直失败"先看 HTTP 状态码/网络请求，比看业务逻辑代码更快定位层级。
3. **502 = 网关连不上后端进程**，几乎总是网络/进程层面的问题（IP 变了、进程没启动、端口没监听），几乎不可能是"业务逻辑 bug"。看到 502 应该直接去查网关日志和目标进程状态，不用读业务代码。
4. **单独重建 compose 里的某个服务后，检查是否有其他服务依赖它的网络地址**（尤其是 nginx/反代类角色，它们倾向于缓存解析结果）。这个项目里 `docker-compose.yml` 显示 `frontend` 通过 nginx 反代到 `api`，以后单独重建 `api`/`worker`/`beat` 中任意一个，习惯性顺手 `docker compose restart frontend`。
