# 排障记录：桌面端"提到的标的"一直显示卡片视图，切换按钮消失

| 项 | 内容 |
|---|---|
| 日期 | 2026-07-12 |
| 现象 | 桌面端浏览器（窗口最大化、缩放100%）打开 AI 总结页，"提到的标的"表格显示成手机端才该有的竖排卡片，且看不到本该在桌面端出现的"切换为卡片视图"按钮 |
| 根因 | antd `Grid.useBreakpoint()` 首次渲染必定返回空对象（视为手机端），而渲染逻辑里手机端分支会**销毁**原始 `<table>` DOM 元素；断点值修正为桌面端后，代码已经找不到表格可处理 |
| 排查耗时 | 约40分钟，中间走了两次弯路（容器没重建 / 浏览器缓存了旧 index.html） |

---

## 1. 现象

用户反馈：桌面端浏览器打开"AI 总结"页，历史生成的总结里"提到的标的"表格显示成一条条竖排卡片（"方向：看多"、"作者理由：..."这种标签+值两行的格式），而预期是横向表格（红绿方向着色、标的名蓝色），且表格右上角应该有一个"切换为卡片视图"按钮——按钮也没出现。

用户强调"窗口已最大化且缩放是100%"，排除了视口宽度本身异常的可能，这是定位到真正根因的关键线索。

## 2. 排查过程（保留走过的弯路）

### 第一次误判：以为是容器没重建

一开始怀疑是 Docker 镜像没重建，改动没生效。验证方式：

```bash
curl -s http://localhost:8090/ | grep -oE 'assets/index-[A-Za-z0-9]+\.js'
curl -s http://localhost:8090/assets/index-xxx.js -o /tmp/bundle.js
grep -c "md-view-toggle\|切换为卡片视图" /tmp/bundle.js
```

结果：bundle hash 已经是新的，且新增代码字符串确实存在于打包产物里。**排除"容器没重建"**——这条路走完发现是错的，但排查方法本身是对的：不要靠"感觉重建过"下结论，直接从产物里 grep 关键字符串验证。

### 第二次误判：以为是浏览器缓存了旧 index.html

检查发现 nginx 对 `/`（`index.html`）没有设置 `Cache-Control: no-cache`，只有 `ETag`/`Last-Modified`，属于 SPA 部署的经典坑——浏览器可能启发式缓存旧 `index.html`（里面指向已过期的旧 JS 文件名）。加了 `add_header Cache-Control "no-cache"` 后重建验证，`curl -sI` 确认响应头生效，bundle hash 也确实换了。

**但用户强制刷新后问题依旧**，说明这不是（唯一）根因，缓存问题修了但没解决用户看到的现象。这里的教训是：确认了一个"看起来合理"的问题并修复后，必须让用户实际验证，不能假设"逻辑上应该好了"就结案。

### 定位到真正根因：追问环境变量排除干扰项

用户之前的截图里，卡片视图的布局特征（每条标的一张卡、"标签：值"两行格式）跟代码里手机端分支 `tableToCardList()` 生成的 DOM 结构完全一致。第一反应是"是不是被误判成手机端了"，但 `isMobile` 的判断逻辑是视口宽度 `< 768px`，用户窗口是最大化桌面浏览器，理论上不该触发。

先用 `AskUserQuestion` 排除了"窗口没最大化"、"浏览器有缩放"这两个最常见的误判原因——用户确认都不是。既然运行时的视口宽度是对的，那问题只能出在**判断逻辑本身的时序**上，不是这次运行时的环境。

读 `antd` 源码定位到真正机制（`node_modules/antd/es/grid/hooks/useBreakpoint.js` + `_util/responsiveObserver.js`）：

```js
function useBreakpoint(refreshOnChange = true, defaultScreens = {}) {
  const screensRef = useRef(defaultScreens);   // 初值是空对象 {}
  const [, forceUpdate] = useForceUpdate();
  const responsiveObserver = useResponsiveObserver();
  useLayoutEffect(() => {                       // 注意：这是 effect，不是渲染期间同步执行
    const token = responsiveObserver.subscribe(supportScreens => {
      screensRef.current = supportScreens;       // 拿到真实断点值后才更新
      if (refreshOnChange) forceUpdate();         // 再触发一次重渲染
    });
    return () => responsiveObserver.unsubscribe(token);
  }, []);
  return screensRef.current;                      // 第一次渲染时，这里读到的还是 {}
}
```

`subscribe()` 内部会立即同步调用一次真实的媒体查询检测（`listener(mql)`），但这段代码是在 `useLayoutEffect` 里执行的——**必然发生在组件完成第一次渲染之后**。React 的渲染顺序决定了：

1. 组件首次渲染，`useBreakpoint()` 返回 `screensRef.current` 的初值 `{}`
2. `MarkdownContent` 里 `const isMobile = !screens.md` 对空对象取值，`screens.md` 是 `undefined`，`isMobile` 被判定为 `true`
3. `useLayoutEffect` 在这次渲染提交后执行，`subscribe()` 拿到真实断点值，调用 `forceUpdate()`
4. 组件第二次渲染，这次 `isMobile` 才是真实值（桌面端场景下是 `false`）

也就是说，**每次这个组件挂载，`isMobile` 必定先经历一次错误的 `true`，再修正为真实值**，跟运行时的视口宽度、浏览器缓存、缩放比例完全无关，是必然发生的两次渲染。

而 `MarkdownContent.tsx` 里驱动 DOM 改造的 `useEffect` 依赖的是 `[html, isMobile]`：

```js
useEffect(() => {
  if (ref.current) enhanceTables(ref.current, isMobile);
}, [html, isMobile]);
```

`isMobile` 从 `true` 变成 `false` 触发了这个 effect 第二次执行，这本身没问题——但 `enhanceTables` 的手机端分支是**破坏性操作**：

```js
const cardList = tableToCardList(table, isTickerTable);
table.parentElement?.replaceChild(cardList, table);   // 直接把原始 <table> 从 DOM 里摘掉
```

第一次执行（`isMobile === true`）把原始 `<table>` 整个替换成了卡片列表 `<div class="md-table-cards">`。第二次执行（`isMobile === false`）时，`root.querySelectorAll("table")` 已经**查不到任何表格**——它已经被第一次执行销毁了，桌面端分支的表格视图 + 切换按钮的构建逻辑根本没有机会跑。最终 DOM 永远停留在第一次渲染产生的卡片视图上。

## 3. 结论 & 修复

**跟数据是否重新生成无关，也跟这次的浏览器窗口状态无关**，是组件设计上没有考虑 DOM 改造的可重入性：破坏性地修改 DOM，却假设这个 effect 只会对"干净的原始 HTML"运行一次。而 antd `useBreakpoint` 首次渲染返回占位值、随后修正的行为，使这个假设在所有场景下都不成立。

修复：每次运行 `enhanceTables` 前，先用最初的 `html` 字符串重置一次 `innerHTML`，保证每次处理的都是干净的原始 DOM，不依赖也不受上一次运行残留状态的影响。

```js
useEffect(() => {
  if (!ref.current) return;
  ref.current.innerHTML = html;      // 用原始 html 重置，抵消上一次的破坏性修改
  enhanceTables(ref.current, isMobile);
}, [html, isMobile]);
```

代价：`isMobile` 每次变化都会整块重新构建 DOM（丢失一次用户已经展开的"展开全部”状态、卡片/表格切换状态），但 `isMobile` 只在窗口跨越 768px 断点或首次挂载时变化，不是高频操作，这个代价可以接受。

## 4. 复用到以后的经验

1. **antd `useBreakpoint()`（以及类似依赖 `useLayoutEffect`/`ResizeObserver` 才能拿到真实值的 hook）第一次渲染永远拿不到真实值**，只能拿到 `defaultScreens`（默认是 `{}`）。任何基于它的判断分支，如果分支内部有"仅执行一次就不可逆"的副作用（销毁 DOM、发起一次性请求、写入某个只初始化一次的缓存），都必须假设这个判断第一次是错的，会有第二次修正。
2. **对现有 DOM 做"破坏性重排"（`replaceChild`、`remove`）的代码，必须显式保证幂等或可重入**，不能依赖"这个 effect 只会跑一次"或"跑的时候输入状态是干净的"这种隐含假设。更安全的默认写法：每次都从源头（不可变的原始数据）重建，而不是在存活的 DOM 上不断叠加/摘除。
3. **用户明确排除的干扰项（这里是"窗口大小/缩放比例正常”）比继续猜环境问题更有效**——一旦运行时环境被排除，问题必然出在代码逻辑本身的时序上，应该去读第三方库的 hook 实现，而不是在应用代码层面反复试参数。
4. **排查中的两次"看起来合理但不是根因"的弯路（容器没重建、浏览器缓存）不是浪费**：这两个问题本身也是真实存在的隐患（旧代码确实需要重建才生效；`index.html` 确实缺 `Cache-Control` 也是需要修的坏味道），修复它们是必要的，只是不足以解释这次的现象。多个问题并存时，逐一排除、每次都让用户验证，比一次性堵所有可能原因更容易定位到真正卡住的那一个。
