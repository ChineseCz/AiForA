## 2. 漏洞详情与修复记录

### SEC-001｜OTP 使用非密码学安全随机数

- **等级**：🔴 高危  
- **类型**：密码学缺陷（CWE-338: Use of Cryptographically Weak Pseudo-Random Number Generator）  
- **位置**：`backend/app/api/routers/public/user_auth.py`（原第 83、163、263 行）  
- **描述**：SMS 验证码、邮箱注册验证码、微信公众号验证码均使用 Python 标准库 `random.choices()`。`random` 基于 Mersenne Twister 算法，其内部状态可通过观测足量输出值还原，攻击者理论上可预测下一个验证码。  
- **影响**：验证码可被预测，导致账号被接管（ATO）。  
- **修复**：将三处替换为密码学安全的 `secrets.choice()`：

```python
# 修复前
code = "".join(random.choices("0123456789", k=settings.sms_code_length))

# 修复后
code = "".join(secrets.choice("0123456789") for _ in range(settings.sms_code_length))
```

- **验证方法**：`grep -r "random.choices" backend/app/` 确认无残留。

### SEC-002｜手机号登录 / 微信验证码登录 / 邮箱注册接口缺少独立限流

- **等级**：🔴 高危  
- **类型**：认证绕过（CWE-307: Improper Restriction of Excessive Authentication Attempts）  
- **位置**：`user_auth.py`：`/api/user/login`、`/api/user/wechat/code-login`、`/api/user/email/register`  
- **描述**：上述三个接口无 `@limiter.limit` 装饰器，仅受全局默认限流 `120/minute` 保护。6位数字 OTP 空间为 10⁶，5 分钟内允许 600 次尝试，单 IP 暴力破解成功率为 0.06%；多 IP 分布式攻击时成功率线性叠加，实际可达。邮箱登录 `/api/user/email/login` 已有限流，三个接口为漏网项。  
- **影响**：验证码/注册流程可被暴力枚举，绕过身份认证。  
- **修复**：为三个接口加 `@limiter.limit(settings.rate_limit_login)`（默认 `5/minute`）：

```python
@router.post("/login")
@limiter.limit(settings.rate_limit_login)  # ← 新增
async def login(request: Request, ...):
```

- **验证方法**：`curl -s -o /dev/null -w "%{http_code}" -X POST http://localhost:8088/api/user/login` 连发 6 次，第 6 次应返回 429。

### SEC-003｜JWT 密钥存在硬编码默认值，生产环境未强制校验

- **等级**：🔴 高危  
- **类型**：密钥管理缺陷（CWE-321: Use of Hard-coded Cryptographic Key）  
- **位置**：`backend/app/core/config.py:69`  
- **描述**：`jwt_secret` 的默认值为字符串字面量 `"change-me-in-production"`。若部署时未通过环境变量覆盖，攻击者可用该已知密钥伪造任意管理员或访客 JWT，完全绕过鉴权。  
- **影响**：任意用户可伪造有效 JWT，获取管理员权限，造成数据泄露或系统被控。  
- **修复**：新增 Pydantic `model_validator`，生产环境（`database_url` 不含 `localhost`）启动时若检测到默认密钥则 `sys.exit(1)`，本地开发仅打 WARN 日志：

```python
@model_validator(mode="after")
def _check_jwt_secret(self) -> "Settings":
    if self.jwt_secret == "change-me-in-production":
        if "localhost" not in self.database_url:
            print("[FATAL] JWT_SECRET 未配置，生产环境禁止启动！", file=sys.stderr)
            sys.exit(1)
        print("[WARN] JWT_SECRET 使用默认值，仅允许本地开发。", file=sys.stderr)
    return self
```

- **验证方法**：在生产 DB URL 环境下以默认 JWT_SECRET 启动，进程应退出并输出 FATAL 日志。

### SEC-004｜`send_sms()` 在异步处理函数中直接阻塞事件循环

- **等级**：🔴 高危（可用性维度）  
- **类型**：阻塞 I/O（CWE-400: Uncontrolled Resource Consumption）  
- **位置**：`user_auth.py` 原第 87 行  
- **描述**：`/api/user/send-code` 是 `async def` 处理函数，但内部直接以同步方式调用 `send_sms(phone, code)`（底层使用 `requests` 库发 HTTP 请求）。同步 HTTP 调用不释放 event loop，整个等待周期（通常几百毫秒到数秒）会阻塞所有并发请求。同一文件的 `send_verification_email` 调用已正确使用 `run_in_threadpool`，此处为遗漏。  
- **影响**：高并发发送验证码时，所有 API 请求（包括无关的读接口）均被阻塞，造成全局响应延迟飙升。  
- **修复**：

```python
# 修复前
ok = send_sms(phone, code)

# 修复后
ok = await run_in_threadpool(send_sms, phone, code)
```

- **验证方法**：并发发送 10 个 `/send-code` 请求，观察 Prometheus 中 `http_request_duration_seconds` 其他接口的 P99 无明显抬升。

### SEC-005｜`/metrics` Prometheus 端点无鉴权公开暴露

- **等级**：🟡 中危  
- **类型**：信息泄露（CWE-200: Exposure of Sensitive Information to an Unauthorized Actor）  
- **位置**：`backend/app/main.py`（原第 59 行）  
- **描述**：`Instrumentator().expose(app, endpoint="/metrics")` 以默认匿名方式注册 `/metrics`，任意公网用户均可访问。该端点暴露所有接口的请求量、错误率、P50/P95/P99 延迟分布，是攻击者进行侦察和漏洞优先级排序的现成地图（可识别低流量管理接口、推断后端处理耗时、定位可用性弱点）。  
- **影响**：内部架构信息泄露，辅助定向攻击。  
- **修复**：不使用 `.expose()`，手动注册 `/metrics` 路由并加 `require_admin` 依赖：

```python
instrumentator = Instrumentator()
instrumentator.instrument(app)

@app.get("/metrics", include_in_schema=False)
async def metrics(_admin: str = Depends(require_admin)):
    return Response(generate_latest(), media_type=CONTENT_TYPE_LATEST)
```

- **验证方法**：匿名访问 `GET /metrics` 返回 401；携带有效管理员 Bearer token 后返回 200 指标数据。

### SEC-006｜生产代码路径使用 `assert` 语句

- **等级**：🟡 中危  
- **类型**：防御性编程缺陷（CWE-617: Reachable Assertion）  
- **位置**：`backend/app/repositories/users.py`（原第 27、49、76 行）  
- **描述**：`get_or_create_by_phone`、`get_or_create_by_openid`、`create_by_email` 三个函数均以 `assert row is not None` 校验 DB 写入后的读取结果。Python 以 `-O`（优化模式）运行时（部分生产 Docker 镜像默认开启），所有 `assert` 语句被编译器静默跳过，函数将返回 `None` 而非抛出异常，导致后续调用方出现难以定位的 `AttributeError`（如 `'NoneType' object has no attribute 'phone'`）。  
- **影响**：在特定部署配置下，用户登录/注册流程抛出 500 错误且错误信息不准确，排查困难。  
- **修复**：改为显式 `raise RuntimeError`：

```python
# 修复前
assert row is not None

# 修复后
if row is None:
    raise RuntimeError(f"INSERT OR IGNORE succeeded but row not found: {phone!r}")
```

- **验证方法**：以 `python -O -c "import app.repositories.users"` 加载模块不报错；在 DB 返回异常数据时日志中出现含 `RuntimeError` 的明确错误消息。

### SEC-007｜CORS 配置过度宽松

- **等级**：🟡 中危  
- **类型**：跨域安全策略缺陷（CWE-942: Permissive Cross-domain Policy）  
- **位置**：`backend/app/main.py`（原第 36–42 行）  
- **描述**：`allow_methods=["*"]` + `allow_headers=["*"]` + `allow_credentials=True` 组合允许任意来源（在 `cors_origins` 白名单内）以任意 HTTP 方法（含 `DELETE`、`PUT`、`PATCH`）携带凭证发起请求。当前后端仅使用 `GET` 和 `POST`，`*` 方法白名单无必要。  
- **影响**：扩大跨站请求伪造（CSRF）的攻击面；未来若误添加危险方法路由，CORS 层不提供任何阻挡。  
- **修复**：

```python
allow_methods=["GET", "POST"],
allow_headers=["Authorization", "Content-Type"],
```

- **验证方法**：从白名单域名发起 `DELETE` 预检请求（`OPTIONS`），响应 `Access-Control-Allow-Methods` 不含 `DELETE`。

### SEC-008｜`/user/me` 串行发起最多 3 次 DB 查询

- **等级**：🟡 中危（性能/并发维度）  
- **类型**：效率缺陷（CWE-405: Asymmetric Resource Consumption）  
- **位置**：`user_auth.py`：`/api/user/me` 端点  
- **描述**：由于 JWT `sub` 字段存储的是手机号/openid/邮箱之一，但 payload 中未记录类型，`/me` 不得不顺序查询三张索引（`phone → openid → email`）以确认用户类型。在最坏情况（邮箱用户）下每次请求产生 3 次串行 DB 往返（每次约 1–5ms × 3 = 3–15ms 额外开销）。  
- **影响**：高频访问 `/me` 时（前端页面加载、刷新 token 等）额外消耗 DB 连接槽；PgBouncer 事务池下连接获取有竞争成本。  
- **修复**：签发 token 时加入 `sty`（sub type）字段，`/me` 据此直接路由到单一查询：

```python
# 签发时
token = create_access_token(phone, typ="visitor", sty="phone", ...)

# /me 中
sty = payload.get("sty", "phone")  # 旧 token 降级兼容
if sty == "wechat":
    user = await users_repo.get_by_openid(session, sub)
elif sty == "email":
    user = await users_repo.get_by_email(session, sub)
else:
    user = await users_repo.get_by_phone(session, sub)
```

**向下兼容**：旧 token（无 `sty` 字段）默认路由至 `phone` 查询，30天内自然淘汰。

- **验证方法**：登录后调用 `/me`，在 PostgreSQL slow query log 中确认只有 1 条 SELECT；旧格式 token 降级路由不报错。

### SEC-009｜`bump_dataver_sync` 每次新建 Redis TCP 连接

- **等级**：🟢 低危（性能维度）  
- **类型**：资源管理缺陷（CWE-405）  
- **位置**：`backend/app/core/cache.py`  
- **描述**：`bump_dataver_sync()` 在每次调用时都执行 `redis.from_url(...)` 新建连接，完成一次 INCR 后立即关闭。在高频数据同步场景（10 分钟一次全市场同步、每次同步后调用）下，每次同步任务完成都会触发 TCP 握手 + Redis AUTH + SELECT + INCR + 关闭，增加约 1–3ms 不必要的延迟。  
- **影响**：单次影响可忽略，但 Redis 服务端会产生大量短连接日志，影响 Redis MONITOR 可读性；在网络抖动时重建连接概率更高。  
- **修复**：使用模块级 `ConnectionPool` 单例：

```python
_sync_pool: "redis.ConnectionPool | None" = None

def _get_sync_pool():
    global _sync_pool
    if _sync_pool is None:
        import redis as _r
        _sync_pool = _r.ConnectionPool.from_url(settings.redis_url, decode_responses=True)
    return _sync_pool

def bump_dataver_sync() -> int:
    try:
        import redis as sync_redis
        client = sync_redis.Redis(connection_pool=_get_sync_pool())
        return client.incr(_DATAVER_KEY)
    except Exception:
        return 0
```

- **验证方法**：`redis-cli monitor` 观察 sync 任务完成后只有 INCR 命令，无 AUTH/SELECT 等连接建立序列。

### SEC-010｜帖子搜索接受单字符关键词，触发全表 LIKE 扫描

- **等级**：🟢 低危  
- **类型**：拒绝服务（CWE-400）  
- **位置**：`backend/app/repositories/posts.py`  
- **描述**：搜索参数 `q` 无最小长度校验，单字符（如 `"a"` 或 `"的"`）即可触发 `WHERE text LIKE '%a%' OR title LIKE '%a%'` 全表扫描。`posts` 表无全文索引，扫描时间随行数线性增长；单字符通配符还会匹配绝大部分行，结果集传输和反序列化成本极高。  
- **影响**：精心构造的低成本请求（单字符关键词，绕过 Cache key 差异化）可使 DB CPU 100% 并使 API 响应超时，形成应用层 DoS。  
- **修复**：在仓储层对 `q` 加最小长度限制（≥ 2 字符）：

```python
if q:
    q_stripped = q.strip()
    if len(q_stripped) < 2:
        return {"total": 0, "items": [], "_warn": "搜索关键词至少 2 个字符"}
    extra += " AND (text LIKE :q OR title LIKE :q)"
    params["q"] = f"%{q_stripped}%"
```

**长期建议**：为 `posts` 表添加 PostgreSQL GIN 全文索引，将 LIKE 改为 `@@` 全文匹配：

```sql
ALTER TABLE posts
  ADD COLUMN fts tsvector
  GENERATED ALWAYS AS (
    to_tsvector('simple', coalesce(title, '') || ' ' || coalesce(text, ''))
  ) STORED;
CREATE INDEX idx_posts_fts ON posts USING GIN(fts);
```

- **验证方法**：`GET /api/posts?q=a` 返回 `{"total": 0, "_warn": "搜索关键词至少 2 个字符"}`，DB 无扫描日志。

## 4. 遗留风险与后续建议

以下问题本次评审不修改代码，但需在后续版本跟进：

### 4.1 JWT 无吊销机制（中危）

访客 Token 有效期 30 天，无 Redis 黑名单或刷新 Token 机制。用户换绑手机/注销账号后，旧 token 在 30 天内仍有效。  
**建议**：引入 `jti`（JWT ID）字段 + Redis Set 维护黑名单，或改为短期 access_token（2h）+ 长期 refresh_token 体系。

### 4.2 选股同步线程池上限偏紧（中危，性能）

`sync_db_pool_size=4 + max_overflow=4`，最多 8 个并发选股任务。每次选股涉及全市场扫描（5000+ 行），耗时数百毫秒到数秒，8 个槽在高并发下会快速耗尽，后续请求排队等待。  
**建议**：将预计算选股结果完全物化（`stock_indicator` 表已有基础），把实时选股路径改为纯缓存读取，根本解决并发上限问题。

### 4.3 `_is_login_required` 缓存过期时雷击（低危）

Redis 缓存 TTL 30秒到期时，大量并发请求同时穿透到 DB 查询 `auth_settings` 表。虽然该查询极轻，但在千人并发下仍会产生短暂峰值。  
**建议**：加 Redis `SET NX` 互斥锁（Mutex Lock），或用 `stale-while-revalidate` 策略：缓存过期后先返回旧值，后台异步刷新。

### 4.4 外部 API 无超时与熔断（低危）

`summarizer.py` 调用 LLM 中转 API、`sina.py`/`eastmoney.py` 调用外部行情接口均无显式超时设置。上游慢响应会导致 Celery worker 槽长时间占用，任务队列积压。  
**建议**：为 OpenAI client 设置 `timeout=30`；外部 HTTP 请求统一加 `requests.get(..., timeout=(5, 30))`；考虑引入指数退避重试（`tenacity` 库）。

### 4.5 管理员密码通过环境变量明文传递（低危）

`ADMIN_PASSWORD` 在容器启动时以明文存在于进程环境变量中，可通过 `docker inspect` 或 `/proc/<pid>/environ` 读取。  
**建议**：改用 Docker Secrets 或 Vault 注入；或仅在首次启动时由运维人员通过 stdin 交互式传入。
